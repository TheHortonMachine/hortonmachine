API

Programs can use the server through two standard APIs, both under {{base}}/api:

  • OGC API - Processes to run the modules: every module is a process, every run a job;
  • STAC API to find and read the files: the shared data, your uploads and the outputs of your jobs.

Access

Create a token in your account page and send it with every request, as the header Authorization: Bearer hm_.... A token acts as its user: it sees only the jobs and uploads of the user, as the pages do. Revoke the tokens you don't use anymore.

The links to the files given by the API, as the results of the jobs and the assets of the catalog, are signed: for a while they work without the header, so that GDAL, QGIS or a browser can open them, as /vsicurl/{{base}}/api/jobs/<id>/files/pit.tif?expires=.... Treat them as the token: they stop working when they expire, when the token is revoked or when the administrators renew the signing key. A signed link opens one file only: for a shapefile, whose parts are separate files, send the header instead, as GDAL does with GDAL_HTTP_HEADERS="Authorization: Bearer hm_...", or prefer GeoPackage.

The files can be read in parts with the Range header, as Range: bytes=0-16383, one range per request, and their size is given by HEAD. The GeoTIFF outputs of the jobs are Cloud Optimized GeoTIFFs, so that a map of a large raster reads only what it shows.

Processes

OGC API - Processes - Part 1: Core, always asynchronous.

GET /apithe landing page, without token
GET /api/conformancethe conformance classes, without token
GET /api/processesthe processes
GET /api/processes/{id}the inputs and outputs of a process
POST /api/processes/{id}/executionrun a process: answers 201 with the job, its address in the Location header
GET /api/jobsyour jobs, filtered by processID, status, limit
GET /api/jobs/{id}the status of a job: accepted, running, successful, failed, dismissed
GET /api/jobs/{id}/resultsthe results of a successful job: the files as hrefs, the computed values inline
GET /api/jobs/{id}/files/{path}a file of a job
DELETE /api/jobs/{id}kill a queued or running job, or delete a finished one with its files

Inputs and outputs

The files are paths in the workspace: data/... for the shared data, uploads/... for your uploads, jobs/<id>/... for the outputs of your jobs; the result of a job can also be given as it is, {"href": "{{base}}/api/jobs/<id>/files/pit.tif"}, and the items of the catalog give the path of their file as hm:path. A table of a GeoPackage follows its path after a #, as data/roads.gpkg#roads. The outputs get default names, as pit.tif or vector.gpkg#vector; outputs chooses which ones are written, all if missing.

Catalog

STAC API 1.0 at {{base}}/api/stac, which the STAC browser of QGIS (Data Source Manager, STAC, with the token as the Authorization header of the connection) and pystac-client read. It is always up to date with the files: the uploads and the jobs at once, the shared data a few seconds after a file stopped changing.

GET /api/stacthe catalog, with a link to each collection
GET /api/stac/conformancethe conformance classes
GET /api/stac/collectionsthe collections you see, with their extents
GET /api/stac/collections/{id}a collection
GET /api/stac/collections/{id}/itemsits items, filtered by bbox, datetime, paged by limit and the next link
GET /api/stac/collections/{id}/items/{itemId}an item, checked against its files
GET, POST /api/stac/searchthe items of all the collections, filtered by collections, ids, bbox, datetime
GET /api/data/files/{path}a file of the shared data
GET /api/uploads/{userId}/files/{path}a file of your uploads

The collections:

  • data: the shared data, one item per file, seen by all the users;
  • uploads: your uploads, one item per file;
  • jobs-<module>, as jobs-Pitfiller: your successful jobs of a module, one item per job with its output files as assets, the module and its parameters, and when the job is removed (expires).

The administrators see the uploads and jobs of all the users. The files that belong to another one, as the parts of a shapefile or the statistics and styles of a raster, are further assets of its item. The rasters and vectors have their footprint in WGS84, their projection (proj:code) and the rasters their bands with statistics (raster:bands); the other files have no geometry. datetime is the time of the last change of a file, or the end of a job, with its start in start_datetime.

Examples

TOKEN=hm_...

curl -H "Authorization: Bearer $TOKEN" {{base}}/api/processes/Pitfiller

curl -i -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"inputs": {"inElev": "data/elevation.tif"}}' \
  {{base}}/api/processes/Pitfiller/execution

curl -H "Authorization: Bearer $TOKEN" {{base}}/api/jobs/<id>
curl -H "Authorization: Bearer $TOKEN" {{base}}/api/jobs/<id>/results
curl -O -H "Authorization: Bearer $TOKEN" {{base}}/api/jobs/<id>/files/pit.tif

curl -H "Authorization: Bearer $TOKEN" "{{base}}/api/stac/search?bbox=10.5,46.0,11.0,46.5&datetime=2026-10-01T00:00:00Z/.."
curl -H "Authorization: Bearer $TOKEN" {{base}}/api/stac/collections/jobs-Pitfiller/items
from pystac_client import Client

catalog = Client.open("{{base}}/api/stac", headers={"Authorization": "Bearer hm_..."})
for item in catalog.search(collections=["data"], bbox=[10.5, 46.0, 11.0, 46.5]).items():
    print(item.id, item.properties["hm:path"], item.assets["data"].href)

The errors are answered as application/problem+json, with the errors of each input in errors.
