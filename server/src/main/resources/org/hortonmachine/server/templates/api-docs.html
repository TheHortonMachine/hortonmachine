API

Programs can use the server through two standard APIs, both under {{base}}/api:

  • OGC API - Processes to run the modules: every module is a process, every run a job;
  • STAC API to find and read the files: the shared ones and yours, uploaded or written by your jobs.

Access

Create a token in your account page and send it with every request, as the header Authorization: Bearer hm_.... A token acts as its user: it sees only the jobs and files of the user, as the pages do. Revoke the tokens you don't use anymore.

The links to the files given by the API, as the results of the jobs and the assets of the catalog, are signed: for a while they work without the header, so that GDAL, QGIS or a browser can open them, as /vsicurl/{{base}}/api/data/files/<your name>/flanginec/pit.tif?expires=.... Treat them as the token: they stop working when they expire, when the token is revoked or when the administrators renew the signing key. A signed link opens one file only: for a shapefile, whose parts are separate files, send the header instead, as GDAL does with GDAL_HTTP_HEADERS="Authorization: Bearer hm_...", or prefer GeoPackage.

The files can be read in parts with the Range header, as Range: bytes=0-16383, one range per request, and their size is given by HEAD. The GeoTIFF outputs of the jobs are Cloud Optimized GeoTIFFs, so that a map of a large raster reads only what it shows.

Data

All the files are in the data, in areas:

  • data/shared/...: the files shared with all the users, written by the administrators only;
  • data/<your name>/...: your files, the uploaded ones and the outputs of your jobs, seen by you and the administrators only; the folder has your username, as data/jane/....

The server knows where each file comes from: uploaded, written by a job, with its module and parameters, or put in the data from outside. When a file is replaced, where the replaced one came from stays in its history.

Processes

OGC API - Processes - Part 1: Core, always asynchronous.

GET /apithe landing page, without token
GET /api/conformancethe conformance classes, without token
GET /api/processesthe processes
GET /api/processes/{id}the inputs and outputs of a process
POST /api/processes/{id}/executionrun a process: answers 201 with the job, its address in the Location header
GET /api/jobsyour jobs, filtered by processID, status, limit
GET /api/jobs/{id}the status of a job: accepted, running, successful, failed, dismissed
GET /api/jobs/{id}/resultsthe results of a successful job: the files as hrefs with their path, the computed values inline
GET /api/jobs/{id}/files/{path}a file of the folder of a job, as its log
DELETE /api/jobs/{id}kill a queued or running job, or delete a finished one; its outputs stay in the data

Inputs and outputs

The input files are paths in the data, as data/shared/flanginec/dtm.tif, or the hrefs of the files of this server, as the results of a job, {"href": "{{base}}/api/data/files/<your name>/flanginec/pit.tif"}; the items of the catalog give the path of their file as hm:path. A table of a GeoPackage follows its path after a #, as data/shared/roads.gpkg#roads.

The outputs get default names, as pit.tif or vector.gpkg#vector; outputs chooses which ones are written, all if missing. A job writes them in its own folder and moves them in the output folder once it succeeded: by default the folder of its first input file in your area, as data/<your name>/flanginec for data/shared/flanginec/dtm.tif, so that they are next to it and in the same collection of the catalog. Without input files it is data/<your name>/results. The request can choose another folder of your area:

{"inputs": {...}, "outputFolder": "data/<your name>/flanginec/runs", "overwrite": true}

An output with the name of an existing file is refused with 409 and the file in errors, unless "overwrite": true.

Catalog

STAC API 1.0 at {{base}}/api/stac, which the STAC browser of the HortonMachine (authentication Bearer token), the STAC browser of QGIS (Data Source Manager, STAC, with the token as the Authorization header of the connection) and pystac-client read. It is always up to date with the files: the uploads and the outputs of the jobs at once, the files put in the data from outside a few seconds after they stopped changing.

GET /api/stacthe catalog, with a link to each collection
GET /api/stac/conformancethe conformance classes
GET /api/stac/collectionsthe collections you see, with their extents
GET /api/stac/collections/{id}a collection
GET /api/stac/collections/{id}/itemsits items, filtered by bbox, datetime, paged by limit and the next link
GET /api/stac/collections/{id}/items/{itemId}an item, checked against its files
GET, POST /api/stac/searchthe items of all the collections, filtered by collections, ids, bbox, datetime
GET /api/data/files/{area}/{path}a file of the shared area or of yours

The collections are the folders: the files of data/shared/flanginec and of data/<your name>/flanginec, at any depth, are the items of the collection flanginec, one item per file. The files directly in an area, outside of any folder, are not in the catalog.

The id of an item tells where its file is, with ~ for /: shared~dem~dtm.tif for data/shared/flanginec/dem/dtm.tif, user~jane~dem~dtm.tif for the same path in the area of jane. Its properties tell the rest:

  • hm:path, the path to give to the processes, hm:area and hm:owner, the user of the area;
  • hm:origin: uploaded, processed or external, with hm:user who uploaded it or ran the job and hm:created;
  • for the outputs of the jobs hm:job, hm:module, hm:parameters and the processing:software of the processing extension;
  • hm:history: the origins of the files it replaced, newest first, each with hm:replaced.

The administrators see the areas of all the users. The files that belong to another one, as the parts of a shapefile or the statistics and styles of a raster, are further assets of its item. The rasters and vectors have their footprint in WGS84, their projection (proj:code) and the rasters their bands with statistics (raster:bands); the other files have no geometry. datetime is the time of the last change of a file.

Examples

TOKEN=hm_...

curl -H "Authorization: Bearer $TOKEN" {{base}}/api/processes/Pitfiller

curl -i -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"inputs": {"inElev": "data/shared/flanginec/elevation.tif"}}' \
  {{base}}/api/processes/Pitfiller/execution

curl -H "Authorization: Bearer $TOKEN" {{base}}/api/jobs/<id>
curl -H "Authorization: Bearer $TOKEN" {{base}}/api/jobs/<id>/results

curl -H "Authorization: Bearer $TOKEN" "{{base}}/api/stac/search?bbox=10.5,46.0,11.0,46.5&datetime=2026-10-01T00:00:00Z/.."
curl -H "Authorization: Bearer $TOKEN" {{base}}/api/stac/collections/flanginec/items
from pystac_client import Client

catalog = Client.open("{{base}}/api/stac", headers={"Authorization": "Bearer hm_..."})
for item in catalog.search(collections=["flanginec"], bbox=[10.5, 46.0, 11.0, 46.5]).items():
    print(item.id, item.properties["hm:path"], item.properties["hm:origin"], item.assets["data"].href)

The errors are answered as application/problem+json, with the errors of each input in errors.
